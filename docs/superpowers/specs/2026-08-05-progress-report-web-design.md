# 运动目标检测 POC 局域网进展网页设计

## 目标

把现有中文阶段报告转成一个可在局域网浏览器中直接访问的单页网站。页面既要让非开发人员快速理解“为什么这样设计、已经做到哪一步、当前结果说明什么”，也要让后续优化人员查到实验数字、证据文件和下一轮优先级。

网站只服务当前 POC，不承担训练管理、用户登录、在线编辑和远程控制实验等功能。

## 已确认的产品方向

- 展示完整的阶段报告，而不是只做几张统计卡片。
- 自动刷新正在运行的 calibration 状态，默认刷新间隔约 10 秒。
- 只读展示，不允许网页启动、停止或修改实验。
- 在局域网监听，当前阶段不发布到公网。
- 第一版以稳定、易读、低维护为目标，后续再扩展交互和可视化。

## 方案比较

### 方案 A：静态报告

优点是实现最少、最稳定；缺点是 calibration 进度不会变化，用户仍需进入终端查看。它不能满足已经确认的自动刷新需求。

### 方案 B：单页报告加轻量本地状态服务

前端负责报告、指标卡、表格、流程图和移动端适配；本地只读服务从运行目录与系统进程中提取状态，向页面返回结构化 JSON。它不侵入算法，不需要数据库，也不会控制实验。该方案最适合当前阶段，确定采用。

### 方案 C：完整实验管理平台

可以提供历史实验、参数编辑、任务启停和用户权限，但会引入数据库、任务调度和权限边界，明显超出当前“先把报告网页化”的范围。

## 信息架构

页面采用一页纵向阅读结构，并提供固定侧边目录：

1. 首屏：项目名称、核心结论、当前阶段和 calibration 实时状态。
2. 项目背景：数据条件、问题难点、为何采用运动优先。
3. 方法流程：稳像残差、运动证据、候选 OBB、tubelet、分类与轨迹。
4. 已完成工作：Tasks 1–10、测试数量和工程能力。
5. 关键实验：十帧 4K smoke、三种已完成 calibration 方法的对比。
6. 性能优化：已定位的瓶颈、修复方法和量化收益。
7. 风险与限制：高误报、OBB 形状不足、evaluation 标注阻塞。
8. 下一步：按 P0–P5 排列优化优先级，并给出实验矩阵。
9. 证据入口：报告原文、对比图、配置和 artifact 路径。

首屏不使用通用后台管理框架，而使用项目特定的“实验作战室”视觉：深色底、运动轨迹线、青绿色实时状态、琥珀色风险提示。数字强调结果，不以装饰性图表替代原始指标。

## 页面组件

### `LiveCalibration`

每约 10 秒请求一次 `/api/status`。显示进程是否存活、运行时长、CPU、内存、当前方法、尺度、最新帧、已完成计算组、暂存目录大小和最后更新时间。

状态分为：

- `running`：进程存活且缓存文件持续更新。
- `stale`：进程存活，但一段时间没有新输出。
- `completed`：最终 calibration artifact 已生成。
- `stopped`：没有进程，也没有最终 artifact。
- `unavailable`：读取权限或数据解析失败。

读取失败时保留上一次有效数据，并明确显示状态陈旧，不让整个报告页面失效。

### `MetricCards` 与 `MethodComparison`

首屏展示 575 项测试、3/8 个已完成计算组、4K 分辨率与当前评估阻塞。方法表展示 Recall@0.25、Recall@0.50、中心命中、mask coverage、proposal 数量和 FP/100 GT；所有指标注明这是 calibration 中间结果。

### `Pipeline`

使用 HTML/CSS 节点和连接线表达：

`视频帧 → 残余稳像 → 多时间偏移运动证据 → 二值 mask → OBB proposal → tubelet → 时序分类 → 轨迹`

小屏幕下改为纵向流程，避免横向滚动。

### `Evidence`

直接展示已生成的三帧对比图，并提供绝对路径文本。图片加载失败时显示可复制路径和原因提示。

## 数据与接口

只读状态接口返回：

```json
{
  "state": "running",
  "updated_at": "2026-08-05T18:15:00+08:00",
  "elapsed_seconds": 38352,
  "cpu_percent": 99.9,
  "rss_bytes": 17532854272,
  "stage_bytes": 3972844748,
  "current_method": "multiscale",
  "current_scale": 1.0,
  "latest_frame": 32,
  "total_frames": 300,
  "completed_groups": 3,
  "total_groups": 8,
  "last_artifact_age_seconds": 4.2,
  "message": "正在生成 multiscale / 1.0 缓存"
}
```

服务端只允许读取以下范围：

- 当前 worktree 下的 `runs/poc-calibration`；
- 当前 worktree 下匹配 `.poc-calibration.*` 的 staging 目录；
- 与 `moving-det calibrate` 对应的本机进程信息。

接口不接收文件路径参数，不提供写操作，不执行来自浏览器的命令。

## 技术结构

- `progress-report-web/`：网页项目目录。
- `app/`：单页界面与样式。
- `server/status.py`：状态发现与解析，输出稳定的数据结构。
- `server/serve.py`：只读局域网服务与 `/api/status`。
- `server/tests/`：状态解析和接口测试。
- 报告正文以本项目已验证的数据固化在页面中；实时接口只更新运行状态，不悄悄改写实验结论。

网页默认监听 `0.0.0.0:8787`。最终交付同时给出本机地址和当前局域网 IP 地址。服务退出后可以用同一个启动入口重新运行。

## 响应式与可访问性

- 桌面端使用固定目录和两栏内容；窄屏改为单栏。
- 所有状态不仅依靠颜色，还带有文字标签。
- 导航、折叠区和链接支持键盘操作，并提供清晰焦点样式。
- 表格在窄屏允许局部横向滚动，不压缩到无法阅读。
- 正文保持足够字号、对比度和行高。

## 验证标准

1. 页面可从同一局域网的另一台设备通过 `http://<局域网IP>:8787` 打开。
2. 页面包含报告的背景、方法、关键结果、限制和下一步，不丢失关键数字。
3. `/api/status` 在 calibration 运行、完成、停止和读取失败时都返回合法 JSON。
4. 浏览器无需访问 NAS 路径即可加载页面；证据图由本地服务安全地映射。
5. 自动刷新失败不会清空报告或上一次有效状态。
6. 项目构建与状态服务测试通过。
7. 网页及服务不修改 calibration staging、最终 artifact 或源数据。

## 非目标

- 不在第一版增加登录、多人编辑、数据库、实验启停和参数修改。
- 不宣称尚未完成的 multiscale、tubelet、0.7 尺度或 evaluation 结果。
- 不把 calibration 中间结果描述为最终模型效果。
- 不修补 evaluation 中的非法 GT。
