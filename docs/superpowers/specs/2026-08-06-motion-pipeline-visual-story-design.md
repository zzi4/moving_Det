# 运动优先处理链可视化说明设计

## 背景

当前局域网阶段报告已经用六张文字卡片概括“残余稳像 → 运动证据 → OBB 候选 → Tubelet → 时序分类 → 轨迹管理”，但读者仍需要依靠想象理解每一步的输入、输出和价值。现有页面末尾的三帧大图同时叠加了运动响应、GT 和大量 proposal，适合作为原始证据，却不适合解释处理链如何逐步收敛。

本次增强把处理链改造成一段可审查的视觉故事：固定同一帧、同一局部区域和同一组颜色，逐步展示每个阶段增加或删除了什么信息，并在图旁给出与该阶段直接相关的指标。前四步只使用真实输入和实验产物；尚未实现的后两步只展示规划机制，并用明显状态标签与真实结果分开。

## 目标

1. 让不了解算法细节的读者能够用一句话说明六个步骤分别解决什么问题。
2. 让读者通过同一区域的连续对照看见“伪运动被削弱、目标运动被增强、像素变成 OBB、候选跨帧连接”的变化。
3. 每个真实步骤至少绑定一项可复核的真实证据或指标，不使用演示性伪数据。
4. 明确揭示当前负面结果：多尺度 proposal 数量过大，现有 Tubelet 只减少约 0.07% proposal。
5. 对规划中的时序分类和轨迹管理，只说明预期机制、输入输出和验收目标，不暗示模型已经完成。

## 非目标

- 不在本次页面增强中修改检测、Tubelet、分类或轨迹算法。
- 不重新解释整份实验报告，也不替换现有关键结果、性能工程和风险章节。
- 不制作看似真实的分类置信度、类别标签、完整轨迹或精度指标。
- 不增加必须由服务器实时计算图像的接口；页面只读取构建前生成的静态 WebP 资产。

## 证据范围与视觉基准

- 数据序列：`motorway_fml_json_v1`
- 中心帧：`000020.jpg`
- 时间上下文：以第 20 帧为中心，使用实现配置中的 `±1 / 3 / 7 / 15` 帧支持
- 统一局部区域：原始 4K 坐标 `x=0, y=720, width=1280, height=720`
- 真实运动缓存：当前 calibration staging 中对应方法、尺度和帧号的 `preview_score` 与 `preview_mask`
- 真实 proposal：对应 artifact 的 `proposals.jsonl`
- 真实 Tubelet：`multiscale_tubelet / scale-1.0 / Z=6` 的 `tubelet_id` 和跨帧 OBB
- 对照指标：artifact 内的 `metrics.json`，报告必须显示指标口径和方法/尺度

这个局部区域同时包含道路车辆、绿化带、树影和道路边缘，能够同时展示真实目标响应与典型背景误响应。所有真实可视化都保持相同裁剪范围和长宽比，避免通过换区域人为改善观感。

## 页面结构

保留现有六步概览卡片，在其下新增“同一场景，逐步收敛”视觉故事。视觉故事由六个纵向章节组成，每章包含：

1. 步骤编号、名称和“真实结果”或“规划中”状态；
2. 一句通俗解释，回答“这一步为什么存在”；
3. 主视觉区域；
4. “输入 → 处理 → 输出”的三段短说明；
5. 一张价值卡，显示真实指标或明确的未来验收目标；
6. 一句当前判断，说明效果是否达到预期。

桌面端采用文字与图像交替左右排列，形成连续阅读节奏；移动端统一改为文字在上、图像在下。真实结果使用薄荷绿状态，负面证据使用琥珀/红色，规划步骤使用中性蓝灰和虚线边框。

## 六步内容设计

### 01 残余稳像

**要回答的问题：** 画面已经做过视频稳定，为什么还需要再次对齐？

**主视觉：** 同一局部区域的“对齐前帧差 / ECC 对齐后帧差”并排图。两张图使用同一色阶，并附一个道路边缘与车辆局部放大窗。页面标出静态道路标线或边缘上的双影如何减弱。

**真实证据：** 使用第 19、20 帧和当前 ECC 配置生成；显示 ECC 估计的平移、旋转、相关系数，以及静态区域平均绝对差的前后变化。若 ECC 对该帧回退，页面必须显示真实回退原因，不用人工挑选替代数值。

**价值说明：** 先消掉相机残余抖动，避免把整个道路边缘误判成运动。

### 02 运动证据

**要回答的问题：** 单帧看不清的小目标，连续帧提供了什么额外信息？

**主视觉：** 原始 RGB 与真实 `preview_score` 热图并排，热图叠加车辆 GT 轮廓；提供“仅运动热图 / 叠加原图”切换按钮。图例解释蓝色为低响应、黄红色为高响应。

**真实证据：** 采用当前表现最有价值的 `frame_diff / scale-0.7 / Z=6`。显示全序列 `Recall@0.25 = 91.26%`、中心命中 `99.19%`、mask coverage `56.16%`，并注明这些是全序列指标，不是单帧指标。

**价值说明：** 运动响应能把大量车辆从纹理有限的 RGB 背景中凸显出来，但树影和细边缘也会响应。

### 03 OBB 候选

**要回答的问题：** 连续的运动像素如何变成后续可以追踪的对象？

**主视觉：** 二值 mask、连通域轮廓和旋转框 proposal 三态切换。默认显示“掩膜 + OBB”，GT 使用青色，proposal 使用红色，正确靠近目标但形状不佳的 proposal 用放大窗说明。

**真实证据：** 与步骤 02 使用同一个 `frame_diff / scale-0.7 / Z=6` artifact。显示全序列 proposal `292,992`、`FP / 100 moving GT = 727.72`、`Recall@0.50 = 7.74%`。同时显示相对 `scale-1.0` 的 proposal 数量下降 `67.81%`、FP 指标下降 `70.33%`，而 Recall@0.25 只下降约 `0.05` 个百分点。

**价值说明：** 这一步完成了“像素 → 可追踪几何对象”的转换；当前主要问题不是没有找到车辆，而是背景碎片太多、OBB 形状不准。

### 04 Tubelet

**要回答的问题：** 为什么不能直接把每一帧的 OBB 当成独立检测结果？

**主视觉：** 第 18–22 帧的同一区域轨迹叠加图。相同 `tubelet_id` 使用同一颜色，中心点之间绘制轨迹线；一次性噪声使用灰色，持续候选使用彩色。提供“连接前 / 连接后”切换。

**真实证据：** 使用 `multiscale / scale-1.0 / Z=6` 与 `multiscale_tubelet / scale-1.0 / Z=6` 的真实 proposal 对照。显示 proposal 从 `2,772,669` 变为 `2,770,752`，只下降约 `0.07%`；`Recall@0.25` 保持 `2.55%`。

**价值说明：** 跨帧连续性理论上可以排除一闪而过的噪声并维持短时漏检，但当前 `min_frames=2` 和连接约束太弱，真实过滤效果不足。这张图的目的既是说明 Tubelet 的价值，也明确暴露当前实现需要优化。

### 05 时序分类

**状态：** 规划中。

**主视觉：** 代码原生 SVG/CSS 示意图，不使用伪造模型截图。图中展示 9–17 帧 RGB crop 与 motion crop 两条输入流，汇合到“类别判断 + OBB 细化”，输出车辆类别、置信度和修正后的旋转框。示意输出使用“预期输出”水印。

**验收目标：** 在 Tubelet 候选已经显著收敛后，报告分类准确率、各类别召回率、OBB Recall@0.50 改善和每条 Tubelet 的类别稳定性。

**价值说明：** 运动负责发现“这里有东西在动”，外观和时间上下文负责判断“它是什么”并修正框形状。

### 06 轨迹管理

**状态：** 规划中。

**主视觉：** 代码原生状态时间线，依次显示 `进入 → 确认 → 短时漏检/遮挡 → 恢复 → 停车 → 离场`。状态节点使用简化 OBB 和轨迹线，明确标记“未观测但轨迹仍存在”的预测区间。

**验收目标：** 后续报告 ID switch、轨迹召回、首次检测延迟、遮挡恢复率、重复轨迹数和离场误保留时长。

**价值说明：** 轨迹状态负责解释短时不可见与停止，只有确认驶出画面或超过生命周期规则后才终止目标，落实“不会凭空消失”的业务先验。

## 静态资产生成

新增一个离线资产生成脚本，从固定输入读取真实帧、NPZ 预览和 JSONL proposal，输出到 `progress-report-web/public/evidence/pipeline/`。脚本要求显式传入 `--data-root` 和 `--run-root`，不自动猜测尚未完成的 staging 目录；本次生成分别使用 `/mnt/nas/Processing_data/mot_sequence` 与当前 `.poc-calibration.suv1ene2` staging。脚本只生成页面资产，不修改实验 artifact。

每张位图同时生成：

- `2x` WebP：桌面高清显示；
- `1x` WebP：移动端和低带宽加载；
- JSON manifest：记录序列、帧号、ROI、方法、尺度、阈值、来源文件和生成时间。

规划中的两张示意图直接使用 React + CSS/SVG 渲染，不生成位图，也不依赖外部图片。

## 组件边界

- `pipeline-story-data.ts`：保存六步文案、状态、指标和静态资产路径，不读取文件系统。
- `pipeline-story.tsx`：负责六步章节结构、状态和无障碍语义。
- `pipeline-visual.tsx`：负责真实图片、切换控件、图例和加载失败回退。
- `planned-stage-diagrams.tsx`：只负责时序分类与轨迹管理的代码原生示意图。
- `generate_pipeline_visuals.py`：只负责从固定 artifact 生成可追溯静态图和 manifest。

页面组件不直接解析大型 JSONL 或 NPZ，避免访问报告时占用 calibration 进程资源。

## 交互与无障碍

- 图像切换使用真正的 `<button>`，支持键盘和清晰焦点状态。
- 每组按钮使用 `aria-pressed` 表示当前图层。
- 所有真实图片提供描述输入、输出和主要问题的中文替代文本。
- 关闭 JavaScript 时，服务端仍渲染每一步的默认静态图、解释和指标。
- `prefers-reduced-motion` 下关闭切换动画。
- 图片加载失败时显示具体资产路径和可读说明，不留空白区域。

## 错误处理与真实性约束

资产生成脚本在以下情况必须失败并指出具体文件：源帧缺失、NPZ 缺少 `preview_score`/`preview_mask`、JSONL 格式错误、帧号或 ROI 越界、指标文件缺少所需字段。

页面通过 manifest 显示证据口径。真实结果不得写入规划图；规划图不得使用“准确率”“提升比例”等未经实验验证的数值。若 calibration 后续结果更新，必须重新运行资产脚本和页面测试，不能只改文案。

## 测试与验收

1. 资产脚本测试验证固定 ROI、帧范围、图像尺寸、manifest 字段和错误输入。
2. 页面渲染测试验证六个步骤、四个“真实结果”状态、两个“规划中”状态及关键真实数值。
3. 组件测试验证图层按钮能切换图片并更新 `aria-pressed`。
4. 构建测试验证所有静态资源路径存在，单张 WebP 不超过 1.5 MiB，整组默认首屏资源按需加载。
5. 浏览器检查覆盖 1440 px 桌面、1024 px 笔记本和 390 px 移动端，不出现横向溢出。
6. 局域网验收要求主页和所有 pipeline 图片返回 HTTP 200，实时 calibration 状态继续正常刷新。

## 成功标准

增强完成后，读者无需阅读源码即可从页面回答：

- 稳像为什么是运动检测前的必要步骤；
- 运动热图如何帮助发现小目标；
- mask 为什么必须转换成 OBB；
- Tubelet 理论上解决什么、当前为什么还没解决好；
- 时序分类和轨迹管理未来分别负责什么；
- 哪些图和数字来自真实实验，哪些内容仍是规划。
